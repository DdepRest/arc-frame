# Формат `.ZKZ` (CCalc 9.12)

Документ фиксирует результат разбора обменного формата CCalc: что читается
надёжно, что осталось закрытым и каким путём это можно добить.

Парсер: `tools/pvc_bridge/zkz_parser.py`.

```bash
python tools/pvc_bridge/zkz_parser.py <файл.ZKZ|каталог>
python tools/pvc_bridge/zkz_parser.py <каталог> --json
python tools/pvc_bridge/zkz_parser.py <файл> --dump-body body.bin
```

## Контейнер

Проверено на 522 файлах `.ZKZ` из
`...\Программа135\Программа\Data` и пользовательских «Заказов Анис»
(2014–2026 гг.). Устройство одинаковое:

| Смещение | Размер | Поле |
| --- | --- | --- |
| 0 | 12 | магия `ADGRASKONZKZ` |
| 12 | 2 | тип записи, uint16 LE |
| 14 | 1 | флаг (во всех наблюдаемых файлах `0x01`) |
| 15 | 4 | длина тела, uint32 LE |
| 19 | N | тело |

Отдельного байта версии нет: после магии ровно 7 байт служебных полей.

`длина тела` во всех 522 файлах равна `размер файла − 19`, то есть файл —
ровно один контейнер без хвостов и без выравнивания. По этому полю парсер
и проверяет целостность.

Типы записей (те же контейнеры лежат в `ccalc.mdb`, таблица `Zakazes`,
поля `Data` и `DataPart2`):

| Тип | Где | Что это |
| --- | --- | --- |
| `0x64` (100) | `.ZKZ` | заказ целиком (для обмена файлами) |
| `0xC4` (196) | `Zakazes.Data` | заказ в базе |
| `0x2C` (44) | `Zakazes.DataPart2` | вторая часть заказа |
| `0x69` (105) | `Zakazchiks.Data` | заказчик |

Метаданные заказа в базе лежат открыто и читаются без расшифровки:
`Id_Zakaz`, `ZakazDate`, `Arhive`, а также размеры блобов `DataSize` /
`DataPart2Size` (они включают 7-байтовый заголовок тела).

## Тело записи: что установлено

Тело обфусцировано самой программой. Проверки и их результат:

| Гипотеза | Проверка | Итог |
| --- | --- | --- |
| Стандартный архив (zlib/raw-deflate/gzip/lzma/bz2) | перебор смещений 0…23 по выборке | не распаковывается |
| Контрольная сумма в первых 4 байтах | сверка с `crc32`/`adler32` остатка | не совпадает |
| Соль/инициализационный вектор на файл | побайтовое сравнение дубликатов и префиксов | **исключено**: одинаковые заказы дают побайтно одинаковые тела, а байты 4–27 совпадают у файлов разных лет |
| Статическая таблица гаммы в exe | поиск известных байтов гаммы в `ProgMain9.12.Dealer+_чистый.exe` | не найдена |
| Гамма = литерал (`ADGRAS`, `ADGRASKONZKZ`, `ZKZ`, …) | XOR/вычитание с повторяющимся ключом | не подтвердилось |
| Генератор Delphi `Random` | перебор seed по 4 известным байтам гаммы | два кандидата, оба дают мусор |
| Текст заказа (cp1251/UTF-16) под фиксированной гаммой | криб-драг адресов двух известных заказов по `Data` и `DataPart2` | совпадения нет |

Что известно точно:

- энтропия тела ≈ 7.9 бит/байт, распределение байтов близко к равномерному;
- преобразование **позиционное**: при одинаковом содержимом тела совпадают
  побайтно, при разном — расходятся с первого отличающегося байта;
- первые ~28 байт у файлов одного типа почти постоянны (меняются единичные
  байты), дальше начинается вариативная часть;
- у разных типов записей гамма разная (`0x64` начинается с `35 80 …`,
  `0xC4` — с `0D 2E …`), то есть ключ/поток зависит как минимум от типа;
- прямого текста (адрес, имя) в теле не видно — оно тоже проходит через
  преобразование.

Вывод: это не архив и не «лёгкий» XOR с известным ключом, а потоковое
кодирование с фиксированным для типа потоком. Без алгоритма из кода
разобрать тело статически не удалось.

## Как добить

1. **Рантайм-дамп.** CCalc расшифровывает тело в память перед показом
   заказа. Снимок процесса в момент открытого `.ZKZ` даёт искомые байты;
   сопоставление «шифртекст ↔ открытый текст» по одному файлу даёт поток
   гаммы целиком, после чего расшифровываются все остальные.
2. **Отладочная сборка/точка останова** на функции чтения контейнера
   (магия `ADGRASKONZKZ` лежит в `.data`, на неё ссылается RTTI-таблица,
   а не код, поэтому поиск по строке к обработчику не ведёт).
3. **RPA-путь (уже работает).** Бот `ccalc_bot.py` открывает заказ в CCalc
   и снимает данные с «Листа заказа» — это единственный на сегодня способ
   получить содержимое заказа без реверса.

## Практический итог

- Заголовок и метаданные `.ZKZ` читаются нативно (`zkz_parser.py`),
  целостность проверяется по полю длины.
- Для импорта заказов в A.R.C. Frame по-прежнему используется RPA: бот
  строит заказ, сохраняет его и пишет реестр `orders/<номер>.json`,
  откуда приложение забирает адрес, сумму, сетку и отлив.
