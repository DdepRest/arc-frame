# План развития AI-функционала A.R.C. Frame

> Рабочее название: **AI Agent Mode**
>
> Цель: превратить AI из текстового помощника в безопасного агента операционной работы с расчётом — от понимания запроса и уточнения параметров до предпросмотра, атомарного выполнения, отмены и объяснения результата.
>
> Статус: **CORE реализован (2026-08-04)** — все направления этого плана выполнены, сборка и тесты 1497/1497 pass. Ключевые модули: `AiActionPlan`/`AiActionStep`, `AiPlanBuilder`, `AiPlanValidator`, `AiPlanExecutor` (атомарный пакет с rollback), `AiLocalCommandRouter` (slash-команды), `AiOrderContextBuilder`, `AiExplanationContextBuilder`, `AiTelemetryService`, план-режим в `AiCommandParser`, карточка плана в `AiAssistantControl.xaml`, guarded undo в `MainWindow.AI.cs`.
>
> Дата составления: 2026-08-04
>
> **Наследие этого плана:** пост-CORE улучшения (централизация предохранителя «не выдумывай», единый источник фактов, промпт из ресурса, разбиение God-классов) переехали в [`project-hardening-plan.md`](project-hardening-plan.md) — Этапы 1–3 (выполнены), Этапы 4–6 (документация/релиз/security hygiene). См. также [`agents/docs/AI_DEFAULTS_POLICY.md`](../agents/docs/AI_DEFAULTS_POLICY.md) для таблицы «silently default vs ask» решений.

---

## 1. Область плана

В план включены выбранные направления:

1. Предпросмотр команд перед выполнением.
2. Локальные slash-команды без обращения к LLM.
3. Отмена последнего действия AI.
4. Богатый контекст текущего заказа.
5. Универсальные формы уточнений для всех основных операций.
6. Агентность и пакетное выполнение нескольких действий.
7. Regenerate / «проще» / «подробнее» без повторного выполнения команд.
8. Экономика токенов, статистика провайдеров и fallback.
9. Объяснение фактических расчётов.
10. Золотой набор регрессионных тестов AI.

Не входят в план:

- распознавание речи;
- долговременная память о клиенте;
- автоматические подсказки-чипы как отдельная функция;
- самостоятельное изменение расчётных формул AI;
- изменение цен, формул Anwis, монтажа, итогов или расчёта откосов.

---

## 2. Главный принцип архитектуры

AI не должен напрямую изменять заказ сразу после ответа модели.

Целевой поток:

```text
Запрос пользователя
    ↓
Локальная команда или LLM
    ↓
Нормализация намерения
    ↓
AiActionPlan
    ↓
Локальная проверка параметров и каталога
    ↓
Форма уточнений, если параметров недостаточно
    ↓
Предпросмотр плана
    ↓
Подтверждение пользователя
    ↓
Атомарное выполнение
    ↓
Результат + Undo всей операции
    ↓
Объяснение результата при необходимости
```

Текущая бизнес-логика приложения остаётся единственным источником истины для:

- цен;
- формул Anwis;
- монтажных надбавок и вычетов;
- размеров;
- итоговых сумм;
- расчёта откосов;
- данных коммерческого предложения.

AI только понимает намерение, собирает параметры, формирует план и переводит фактический результат в понятный текст.

---

## 3. Базовые правила поведения AI

### 3.1. Безопасные значения можно предугадывать

AI может использовать без отдельного вопроса:

- количество `1`, если оно не указано;
- стандартный цвет, если у товара только один допустимый цвет;
- цену из действующего каталога;
- тип товара, если запрос однозначно его определяет;
- монтаж только при явном указании пользователя.

В предпросмотре такие значения помечаются:

```text
Количество: 1 (по умолчанию)
```

### 3.2. Критичные параметры нельзя выдумывать

Нужно запросить уточнение, если отсутствуют или неоднозначны:

- ширина;
- высота;
- глубина откоса;
- режим Anwis, если он обязателен для сценария;
- конкретная позиция для изменения или удаления;
- цена при явном запросе на изменение;
- товар, если в запросе совпадает несколько вариантов.

### 3.3. Любое изменение заказа прозрачно

Пользователь всегда должен видеть:

- что будет изменено;
- какие значения приняты по умолчанию;
- какие позиции затронуты;
- предварительный итог;
- можно ли отменить действие.

# 5. Этап 1 — локальные slash-команды

## Цель

Сделать часто используемые действия мгновенными, предсказуемыми и независимыми от сети и токенов.

## Команды

### Информация

```text
/товары
/цены
/итоги
/статус
/последняя
```

### Управление расчётом

```text
/отменить
/повторить
/очистить
```

### Управление ответом AI

```text
/повторить-ответ
/объясни
```

Также поддержать английские варианты:

```text
/products
/prices
/totals
/status
/undo
/redo
/clear
/explain
```

## Поведение

- `/товары` — локальный каталог;
- `/цены` — локальные цены без LLM;
- `/итоги` — локальные итоги заказа;
- `/статус` — позиции, сумма, активная модель и состояние провайдеров;
- `/последняя` — подробности последней позиции;
- `/отменить` — Undo без LLM;
- `/повторить` — Redo без LLM;
- `/очистить` — локальный план очистки с подтверждением;
- `/объясни` — подготовка фактического контекста и запрос объяснения у LLM.

Неизвестная slash-команда показывает понятную ошибку и список доступных команд. Она не должна молча уходить в LLM.

## Предлагаемые файлы

```text
Services/AiLocalCommandRouter.cs
Tests/Services/AiLocalCommandRouterTests.cs
```

Изменить:

```text
ViewModels/AiAssistantViewModel.cs
Controls/AiAssistantControl.xaml
```

## Критерии готовности

- команды работают при отключённом интернете;
- slash-команды не расходуют токены;
- изменяющие slash-команды используют общий план и подтверждение;
- `/отменить` и `/повторить` корректно обновляют UI и итоги.

# 6. Этап 2 — богатый контекст текущего заказа

## Цель

Дать AI достоверную картину текущего заказа, чтобы он мог работать с существующими позициями, а не угадывать их.

## Новый контекст

```text
Models/AiOrderContext.cs
Services/AiOrderContextBuilder.cs
```

## Содержимое контекста

### Общие итоги

- количество активных позиций;
- итоговая сумма;
- сумма основного КП;
- сумма дополнительных КП;
- количество штук;
- общая площадь;
- общая длина в погонных метрах.

Использовать существующий `TotalInfo`, `CalculateTotal()` и `ClientInfo.AdditionalKpsTotal`.

### Группировки

- по товарам;
- по цветам;
- по монтажу;
- по категориям:
  - сетки;
  - фасадные изделия;
  - комплектующие;
  - услуги;
  - откосы.

### Данные позиций

- стабильный идентификатор;
- номер позиции для UI;
- название;
- цвет;
- ширина и высота;
- количество;
- базовая цена;
- итог без монтажа;
- итог с монтажом;
- режим монтажа;
- режим Anwis;
- единица измерения;
- признаки площади, погонных метров или штучного товара.

### Размеры

Для Anwis обязательно передавать отдельно:

- введённые размеры;
- расчётные размеры;
- заводские размеры;
- размеры в КП;
- режим Anwis.

Нельзя смешивать эти четыре типа размеров.

### Откосы

- размеры окна;
- глубина;
- количество;
- режим экономии;
- материалы;
- материалы отдельно от работы;
- итоговый `GrandTotal`.

### Клиент

Передавать только необходимые поля:

- имя;
- адрес;
- номер договора.

API-ключи и секреты в контекст не попадают.

## Примеры запросов

```text
Сколько у меня сеток?

Удали все коричневые изделия.

Увеличь количество последней позиции до двух.

Сколько будет стоить заказ с монтажом?

Какая позиция самая дорогая?

Покажи разницу между сетками и отливами.
```

## Критерии готовности

- AI отвечает по фактическим данным заказа;
- локальные итоги совпадают с UI;
- контекст ограничен актуальными данными и не раздувает prompt;
- персональные данные и секреты не передаются лишним запросам.

# 7. Этап 3 — предпросмотр и подтверждение действий

## Цель

Перед выполнением показать человеку точный план изменений.

## Политика

### Без подтверждения

- обычные вопросы;
- `/товары`;
- `/цены`;
- `/итоги`;
- объяснение готового расчёта;
- просмотр статуса.

### С обязательным подтверждением

- добавление товара;
- изменение позиции;
- удаление;
- очистка заказа;
- изменение цены;
- массовое действие;
- любой пакет из нескольких шагов.

## Пример карточки

```text
План действий

1. Добавить Anwis
   Цвет: Белый
   Размер: 700×1400 мм
   Режим: ББ60
   Количество: 1 (по умолчанию)
   Монтаж: не указан

2. Добавить Отлив
   Цвет: Коричневый
   Размер: 200×1500 мм
   Количество: 2
   Монтаж: с монтажом

Предварительно: 3 позиции

[Изменить] [Выполнить] [Отмена]
```

## Предварительная цена

Предпросмотр не должен дублировать формулы вручную.

Варианты:

1. рассчитать на изолированной копии через существующий расчётный путь;
2. выделить безопасный preview-вызов из существующей логики;
3. использовать уже созданные `OrderItem` только в отдельном непубликуемом состоянии.

Запрещено создавать упрощённую AI-формулу цены, которая может расходиться с приложением.

## UI-модель сообщения

Добавить в `AiChatMessage`:

```text
ActionPlan
IsAwaitingConfirmation
IsExecuted
IsCancelled
CanUndo
ExecutionResult
```

Создать карточку плана в AI-контроле или отдельный reusable control.

## Критерии готовности

- пользователь видит полный список изменений;
- план можно отредактировать до выполнения;
- опасные действия не выполняются по одному только ответу модели;
- после отмены состояние заказа не меняется.

# 8. Этап 4 — универсальные формы уточнений

## Цель

Для любого типа операции показывать компактную форму только с нужными полями.

Не создавать одну огромную форму со всеми параметрами. Форма должна динамически зависеть от типа операции, товара и контекста.

## Общая модель поля

```text
AiFieldDefinition
├── Key
├── Label
├── FieldType
├── IsRequired
├── VisibilityRule
├── ValidationRule
├── DefaultValue
└── HelpText
```

## 8.1. AddItem

Общие поля:

- тип товара;
- цвет;
- ширина;
- высота;
- количество;
- монтаж.

Для Anwis:

- ББ60;
- ББ70;
- ПП;
- Проём;
- Габарит.

Для ручных позиций:

- название;
- цена;
- количество;
- комментарий.

Список товаров и цветов берётся из каталога, а не из статического текста AI.

## 8.2. CalcSlope

- ширина окна;
- высота окна;
- глубина;
- количество окон;
- режим экономии;
- кнопка «Рассчитать».

После заполнения пользователь должен увидеть расчёт материалов и итог до добавления результата в КП.

## 8.3. UpdateItems

- выбор конкретных позиций галочками;
- фильтр по типу;
- фильтр по категории;
- фильтр по цвету;
- изменение монтажа;
- изменение цены;
- изменение цвета;
- изменение режима Anwis.

## 8.4. DeleteItems

Варианты выбора:

- последняя позиция;
- конкретная позиция;
- несколько позиций;
- категория;
- цвет;
- все позиции.

Показывать количество удаляемых позиций и текущую сумму.

## 8.5. ClearAll

Показывать:

```text
Будет удалено: 8 позиций
Текущая сумма: 34 200 ₽
Действие можно отменить через Undo.
```

Очистка всегда требует подтверждения.

## Критерии готовности

- форма появляется для любой команды, которой не хватает параметров;
- отображаются только релевантные поля;
- локальная валидация не зависит от ответа LLM;
- неверные размеры, цвет или режим блокируют выполнение;
- заполненная форма превращается в `AiActionPlan`, а не сразу меняет заказ.

# 9. Этап 5 — агентность и пакетные команды

## Цель

Позволить AI планировать и выполнять несколько связанных действий в одном запросе.

## Пример

Запрос:

```text
Добавь белую сетку Anwis 700×1400 ББ60,
два коричневых отлива 200×1500 с монтажом
и поставь монтаж на новые позиции.
```

План:

```text
Шаг 1. Добавить Anwis.
Шаг 2. Добавить два Отлива.
Шаг 3. Применить монтаж к позициям шагов 1–2.
```

Шаг 3 зависит от шагов 1 и 2.

## Алгоритм

1. Разобрать запрос на действия.
2. Построить единый `AiActionPlan`.
3. Проверить каждый шаг.
4. Проверить зависимости.
5. Проверить неоднозначности.
6. Показать единый предпросмотр.
7. Получить одно подтверждение.
8. Создать один snapshot до начала.
9. Выполнить шаги по порядку.
10. При ошибке любого шага откатить весь пакет.
11. Показать общий результат.

## Атомарность

Для пакета используется существующая система:

```text
OrderSnapshot
UndoRedoService
RestoreFromSnapshot
```

Один пакет — один Undo-шаг. Нельзя оставлять заказ в частично изменённом состоянии.

## Зависимые шаги

Поддержать ссылки на результаты предыдущих шагов:

```text
CreatedItemIdsFromStep(1)
CreatedItemIdsFromStep(2)
```

Это позволит выполнить:

```text
Добавь товар и поставь монтаж именно на него.
```

## Первая версия агентности

Включить:

- несколько AddItem;
- несколько UpdateItems;
- несколько DeleteItems;
- AddItem + UpdateItems;
- подготовку CalcSlope с параметрами.

Не включать в первую версию полностью автоматическое управление сложными интерактивными панелями, где требуется ручная проверка большого количества материалов.

## Критерии готовности

- пакет проверяется до первого изменения заказа;
- любой сбой вызывает полный откат;
- единый предпросмотр показывает все шаги;
- один Undo отменяет весь пакет;
- зависимости между шагами работают предсказуемо.

# 10. Этап 6 — Undo последнего действия AI

## Цель

Позволить одним нажатием отменить отдельную AI-операцию или весь пакет.

## UI

После успешного выполнения:

```text
✅ Выполнено 3 действия
[Отменить действие]
```

После отмены:

```text
↩ Действие AI отменено
[Повторить]
```

## Метаданные Undo

Расширить `UndoRedoService` или добавить запись операции:

```text
UndoEntry
├── Snapshot
├── Source: User | AiSingleAction | AiBatchAction | Import
├── OperationId
├── Description
├── CreatedAt
└── CanRestoreSafely
```

## Защита от потери ручных изменений

Если после AI пользователь уже изменил заказ, показать предупреждение:

```text
После этого действия были внесены другие изменения.
Безопасная отмена всего AI-действия невозможна.
Используйте обычный Undo по шагам.
```

Нельзя молча восстанавливать старый snapshot поверх новых ручных изменений.

## Критерии готовности

- одиночное действие AI отменяется отдельно;
- пакет отменяется одним Undo;
- Redo возвращает отменённое действие;
- ручные изменения пользователя не затираются без предупреждения.

# 11. Этап 7 — Regenerate без дублей

## Цель

Позволить попросить AI переписать ответ, не повторяя уже выполненные команды.

## Кнопки

```text
Повторить ответ
Проще
Подробнее
Исправить
```

## Режимы

### Повторить текст

Генерирует новый текст без исполнения команды.

### Повторить план

Создаёт новый предпросмотр, но не выполняет его автоматически.

### Проще / подробнее

Передаёт уже полученный результат и просит изменить стиль объяснения.

## Защита от повторного AddItem

Хранить:

```text
RequestId
SourceMessageId
PlanId
ExecutionStatus
ExecutedActionIds
```

Если план уже выполнен, повторная генерация может вернуть только объяснение или новый проект плана. Она не должна снова вызывать выполнение старой команды.

## Критерии готовности

- повтор ответа не добавляет товар второй раз;
- «проще» не меняет заказ;
- повтор плана снова требует подтверждения;
- история чата сохраняет связь между исходным запросом и регенерацией.

# 12. Этап 8 — экономика токенов и состояние провайдеров

## Цель

Показывать пользователю, какая модель ответила, сколько занял запрос и почему произошёл fallback.

## Метрики запроса

```text
Models/AiRequestMetrics.cs
```

Собирать:

- провайдер;
- модель;
- время начала;
- длительность;
- номер попытки;
- число fallback-переключений;
- HTTP-статус;
- причина ошибки;
- входные токены, если API их вернул;
- выходные токены, если API их вернул;
- размер истории;
- размер контекста заказа;
- число шагов плана;
- результат выполнения.

Если API не возвращает usage, показывать `неизвестно`, а не выдуманную точную цифру.

## UI

В сообщении или статусной строке:

```text
NVIDIA · Nemotron
Ответ: 2,4 с
Попытка: 1
Fallback: нет
```

При переключении:

```text
OpenRouter: 429
Повтор: 2 из 3
Переключение на NVIDIA
```

В настройках — статистика текущей сессии:

```text
Запросов: 18
Успешных: 17
Fallback: 4
Среднее время: 2,1 с
```

## Приватность

Не сохранять в telemetry:

- API-ключи;
- полные тексты запросов;
- содержимое заказов;
- персональные данные клиентов.

## Критерии готовности

- модель и провайдер фактического ответа видны пользователю;
- retries и fallback объясняются понятно;
- usage отображается только при наличии фактических данных;
- секреты и полные данные заказа не попадают в статистику.

# 13. Этап 9 — объяснение фактических расчётов

## Цель

Пусть AI объясняет уже выполненный приложением расчёт, а не придумывает собственные формулы.

## Команды

```text
Почему эта позиция стоит столько?

Объясни расчёт последней сетки.

Почему сумма с монтажом такая?

Откуда взялась цена откосов?

Покажи разницу между расчётными и заводскими размерами.
```

Локальные варианты:

```text
/объясни
/объясни последнюю
/объясни позицию 3
```

## Контекст объяснения

```text
Models/AiCalculationExplanationContext.cs
Services/AiExplanationContextBuilder.cs
```

Для товара передавать:

- название;
- цвет;
- введённые размеры;
- расчётные размеры;
- заводские размеры;
- количество;
- базовую цену;
- монтаж;
- поправки;
- итог без монтажа;
- итог с монтажом;
- единицу измерения.

Для Anwis дополнительно:

- режим;
- фактически применённую формулу;
- размеры до коррекции;
- размеры после коррекции.

Для откосов:

- материалы;
- количества;
- цены материалов;
- работу;
- экономию;
- `GrandTotal`.

## UI

Добавить кнопку:

```text
[Объяснить расчёт]
```

Она может появляться:

- на сообщении AI;
- в карточке позиции;
- в предпросмотре;
- в контекстном меню заказа.

## Ограничения

AI не может:

- менять цену;
- заменять фактический итог;
- добавлять собственную формулу;
- утверждать расчёт, если приложение не передало исходные данные.

## Критерии готовности

- объяснение совпадает с числовыми данными приложения;
- явно различаются введённые, расчётные и заводские размеры;
- для Anwis показывается выбранный режим;
- объяснение не создаёт новую команду изменения заказа.

# 14. Этап 10 — золотой набор регрессионных тестов

## Что это такое

Это внутренняя система контроля качества AI, а не пользовательская функция.

Она содержит реальные фразы менеджеров и ожидаемые намерения, параметры и правила безопасности.

Пример:

```text
Фраза:
Добавь белую Anwis 700×1400 ББ60

Ожидается:
intent: AddItem
type: Anwis
color: Белый
width: 700
height: 1400
anwis_mode: Брусбокс60
quantity: 1
requires_confirmation: true
```

## Файлы

```text
Tests/AI/golden-cases.json
Tests/Services/AiGoldenCaseTests.cs
```

## Категории кейсов

### AddItem

- полностью заполненный запрос;
- отсутствующий цвет;
- отсутствующий размер;
- разные названия сеток;
- опечатки и разговорные сокращения;
- монтаж;
- дробное количество;
- ручные позиции.

### Anwis

- ББ60;
- ББ70;
- ПП;
- Проём;
- Габарит;
- отсутствие режима;
- отличие «Проём» от «Габарит»;
- проверка введённых и расчётных размеров.

### CalcSlope

- ширина;
- высота;
- глубина;
- количество;
- отсутствие одного параметра;
- несколько окон.

### UpdateItems

- конкретная позиция;
- категория;
- цвет;
- несколько критериев;
- монтаж;
- цена;
- режим Anwis.

### DeleteItems

- удалить последнюю;
- удалить категорию;
- удалить цвет;
- выбрать несколько позиций;
- удалить весь расчёт.

### Batch

- два AddItem;
- AddItem + UpdateItems;
- несколько разных категорий;
- зависимые шаги;
- ошибка на втором шаге;
- проверка полного отката.

### Безопасность

- повтор уже исполненной команды;
- regenerate;
- неоднозначная позиция;
- изменение цены без подтверждения;
- очистка заказа;
- недостаточные параметры;
- попытка выполнить частичный пакет.

## Формат кейса

Каждый кейс содержит:

```text
id
user_text
expected_mode
expected_intent
expected_steps
expected_parameters
expected_confirmation_policy
expected_clarification_fields
```

## Уровни тестирования

### Offline

Обычный `dotnet test` проверяет:

- parser;
- нормализацию параметров;
- формы;
- локальную валидацию;
- построение плана;
- защиту от дублей;
- атомарное выполнение;
- Undo/Redo.

API не вызывается.

### Recorded model responses

Сохранённые ответы моделей проверяют:

- JSON разных форматов;
- Markdown вокруг JSON;
- неполные ответы;
- ошибки моделей;
- fallback;
- устойчивость парсера.

### Онлайн-проверки

Запускаются вручную и не блокируют обычный CI:

- актуальный prompt;
- сравнение моделей;
- качество распознавания;
- статистика реальных провайдеров.

## Критерии готовности

- набор содержит реальные сценарии менеджеров;
- каждый найденный AI-баг добавляется отдельным кейсом;
- изменения parser/prompt/plan проходят offline-набор;
- онлайн-тесты не расходуют токены в обычной сборке.

# 20. Итоговые критерии завершения AI Agent Mode

Функционал считается реализованным, когда:

- все изменяющие действия проходят через локально проверяемый план;
- пользователь видит предпросмотр до изменения заказа;
- формы уточнений существуют для AddItem, CalcSlope, UpdateItems, DeleteItems и ClearAll;
- AI умеет обрабатывать несколько действий в одном запросе;
- пакет проверяется целиком до первого изменения;
- ошибка вызывает полный откат;
- один Undo отменяет весь пакет;
- regenerate не создаёт дубликаты;
- slash-команды работают без сети;
- AI получает актуальные итоги и позиции заказа;
- модель, провайдер, retries и fallback видны пользователю;
- AI объясняет фактические данные приложения;
- golden suite покрывает реальные фразы менеджеров;
- online-проверки моделей отделены от обычного CI;
- все тесты и документация обновлены;
- формулы, цены, размеры, монтаж и итоги не изменены без отдельного согласованного плана.
